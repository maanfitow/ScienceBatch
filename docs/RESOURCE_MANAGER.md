# Project Resource Analysis Contract

This document describes the offline analysis and planning API shared by the automation service and desktop resource manager. Analysis reads a captured project snapshot and the pinned local resource catalog. It does not create cache directories, access the network, modify the project, or compile TeX or Typst.

## Operations

`resources.analyze` returns the current resource summary for an explicitly selected project or captured workspace snapshot. `resources.plan` returns the same summary after checking the required `expectedInputDigest`; if supplied, `expectedPlanDigest` must also match the newly resolved plan. `resources.list` returns one page of requirements and unresolved references and requires `expectedPlanDigest`. Its cursor is bound to that digest. Changing the selected project, main file, engine, workspace identity, snapshot bytes, manifest, selection, preprocessing revision, or pinned catalog changes the digest and invalidates stale plans and cursors.

The Rust service exposes `analyze_snapshot(snapshot, args)` for transport adapters and `resolved_plan(snapshot, args)` for preparation and Tauri integration. Plan rows carry `resourceSchemaVersion: 1`, `inputDigest`, `planDigest`, engine, main file, selection, availability, evidence, byte counts, and explicit unresolved references. `resources.list` pages both requirement and unknown rows, so the summary's `unknownOmitted` count is recoverable through pagination.

## Project manifest and selectors

The optional UTF-8 project file `sciencebatch.resources.json` has schema version 1:

```json
{
  "schemaVersion": 1,
  "engine": "latex",
  "requirements": [
    { "kind": "pack", "id": "latex-ieeetran" },
    { "kind": "package", "id": "fontawesome5" },
    { "kind": "resource", "id": "custom-resource.sty" }
  ]
}
```

Only `schemaVersion`, optional `engine`, and `requirements` are accepted. Selectors are exact `pack`, `package`, or pinned bundle `resource` identifiers. URLs, scripts, arbitrary CTAN versions, and paths outside the bundle are rejected. The manifest is read from the captured snapshot (including in-memory overlays); analysis never edits it. The mandatory detected base closure and transitive references cannot be removed by selection.

The analyzer follows reachable literal LaTeX package, class, input, include, bibliography-style, and local asset references. Class references resolve `.cls`; package references resolve `.sty`. Project-local classes and packages take precedence over bundle packs, and project-local `simpleicons.sty` takes precedence over the embedded SimpleIcons files. Recursive local inputs are cycle-safe. The explicitly recorded cold format-generation resource set remains pinned even when a project has same-path files; both the local file and required bundle copy appear in the plan because format generation reads the pinned bundle. The default LaTeX starter's `sample.png` and `references.bib` are never substituted for missing project assets. Typst reports its engine assets as embedded and follows literal local imports and images; it does not invent downloadable packages.

Macro-valued names, unsupported dynamic references, and unresolved conditionals appear as unknown rows. A plan can therefore report `prepared_known_set` only for its known selected requirements; uncertainty remains visible in the same response and paged list.

## Availability and identity

Requirement availability is one of `local`, `embedded`, `cached_verified`, `missing`, or `invalid`; provider identity is reported separately as `project_local`, `embedded`, or `pinned_bundle`. The built-in LaTeX Showcase/Scratchpad closure is reported with provider `pinned_bundle` and availability `embedded`; its exact indexed bodies and the bundle index are included in the application and checked against the catalog. Other cached resources are accepted only after checking their indexed byte length and SHA-256. For LaTeX, `bundleMetadataState` is `embedded` when the on-disk bundle metadata is absent, `cached_verified` when present and valid, or `invalid` when existing metadata conflicts with the pinned identity. `summary.metadataStorageBytes` is zero for the embedded or verified states. An invalid existing identity blocks the plan and cannot be repaired automatically. Cache state is deliberately excluded from `inputDigest` and `planDigest`, so a cache warming between analysis and preparation does not make the project plan stale. A plan digest binds the selected set and paths to the input digest, pinned bundle/index/catalog identities, and preprocessing revision. Offsets and hashes always come from the compiled-in catalog; callers cannot provide resource descriptors.

## Bounds and errors

The project snapshot remains subject to the automation snapshot limits. Resource manifests are limited to 1 MiB; selectors to 1,000; each selector ID, project path, and scanned resource expression to 4,096 UTF-8 bytes; and resolved plan rows to 20,000. List pages contain at most 200 rows, and summary/list JSON is limited to 1 MiB. Exceeding resource-specific bounds returns `resource.limit_exceeded`. Invalid manifests, selectors, engine combinations, snapshots, catalogs, or stale digests return structured `resources.*` errors. Analysis performs no repair or automatic download.

## Catalog provenance and coverage

The embedded catalog is generated from the already prepared QA bundle. Its pinned bundle digest is `6ffe055852f8faf66c0acbe1a7fb27f87b869a90bad1204f3bf4d9683f597c7c`; its original 5,143,485-byte index digest is `0fb434b0fa5fdebea7f767ed9c31939c99a780d6f95cd3f540aae55910bb5697`. It contains metadata for 134,980 indexed resources and no provider resource bodies. SHA-256 values detect local corruption and bind the metadata to that capture; they are not independent provider authentication.

Pack resource lists are unions of locally captured successful offline fixture traces and a baseline article trace. `formatResources` separately records all 244 paths from the cold format-generation baseline and prevents project-local same-path files from replacing those required bundle entries. The 358 indexed resources used by the built-in Showcase are embedded as the starter closure; their source capture, archive bounds, and deterministic rebuild command are documented in `RESOURCE_CATALOG.md`. The fixture traces for the academic classes and supported icon sets completed with zero Internet socket connections. The resume-font pack uses the successful `fontspec` plus Cochineal/Cabin/Inconsolata fixture. These measured sets are useful known closures for their fixtures, not proof of complete TeX dependency closure. Static literal source metadata supplements those sets; dynamic expressions remain unresolved. Rebuilding the catalog requires the original validated QA cache and the local catalog builder documented in `RESOURCE_CATALOG.md`.

## Selective preparation

`resources.prepare_project` requires explicit resource-download permission and an `expectedPlanDigest` from a fresh analysis. It resolves the same captured snapshot again before starting a worker; stale plans fail before cache writes or subprocess creation. `expectedInputDigest` is checked when supplied. The worker accepts only normalized schema-1 bundle paths, the pinned bundle/index identities, and caller budgets; offsets and SHA-256 values are derived from the embedded catalog. It never accepts URLs or client-provided descriptors. The pinned original index and digest metadata are seeded only during this explicit operation when downloadable resources need them; the embedded starter closure is already ready and skipped by preparation.

Preparation reuses only files whose indexed length and SHA-256 match. Downloaded slices are checked before publication; complete files are written into a private job staging directory and atomically renamed into the shared bundle cache. A cache-wide quota lock followed by a per-bundle cross-process writer lock coordinates selective jobs and the existing full-bundle preparation worker. Interrupted jobs are reaped, their job-owned staging directory is removed, and already verified files remain reusable. The worker times out after 30 minutes. It does not evict cache entries.

During explicit preparation on Unix, user-owned managed cache directories left group- or world-writable by a permissive umask are secured through a no-follow directory handle: the worker removes only group/world write bits and preserves the remaining permission bits. It rejects symlinked, replaced, or foreign-owned managed directories. Newly created Unix cache directories are made private, and permission-setting failures stop preparation. Other platforms retain their filesystem access controls. Analysis and application startup do not repair or otherwise mutate cache permissions.

`maxDownloadBytes` and `maxStorageBytes` default to 512 MiB each and can be raised up to 8 GiB. `maxStorageBytes` applies to selected resource files plus their conservative allocation and directory allowance; the shared bundle index/digest are reported separately through `metadataStorageBytes` and still count toward the global 8 GiB cache cap and available-space checks. The selected resources are rejected before download when their estimated transfer or conservative allocated-storage reservation exceeds those limits. Storage reservation rounds each resource to a 4 KiB allocation unit and includes an inode/directory allowance, newly needed directories, and publication headroom. The cache walk counts allocated Unix blocks (or file lengths on other platforms), directory overhead, and enforces a 200,000-file bound and an 8 GiB cache cap. Free-space query failures fail closed. Transfer estimates use the same range coalescing rules as the downloader, including coalesced gaps. The worker reports `firstAttemptTransferEstimateBytes` and `budgetChargedBytes` separately: the latter is a conservative downloader accounting value and can include failed or retried ranges, so it is not presented as exact wire bytes on partial failure. Successful no-retry transfers report the exact first-attempt range amount in `bytesDownloaded`.

The isolated worker streams bounded NDJSON progress and one terminal result. Cancellation, timeout, malformed or oversized frames, stderr overflow, and parent request drop all kill and reap the child before releasing its shared worker permit. Preparation itself never compiles the project. Typst preparation returns the embedded known set without network transfer and keeps unresolved references in its bounded plan summary.

## Desktop quick start

Choose **Dependencies** in the left activity bar to inspect the open project. The panel lists only its detected, manifest-declared, and known transitive resource files, with indexed sizes and availability. Its download action runs preparation directly and displays batch progress; a file changes to downloaded only after verified atomic publication. File sizes are resource payload lengths, while the transfer estimate can include gaps in coalesced HTTP ranges. **Tools → Project Resources** remains a compact readiness view for the current workspace. The dialog opens in a compact 520 px layout and automatically runs read-only analysis while it remains open. The Dependencies panel also observes changes while visible. Relevant workspace changes queue another analysis; overlapping refresh requests are serialized and coalesced. Analysis does not compile or download resources.

The dialog detects resources from the current project and its manifest automatically. It shows whether files are missing, the estimated download, and one explicit action: **Download required files**, **Finish setup**, **Done**, **Resume download**, or **Try again**. It does not show resource selectors, file lists, provenance, or technical error details. The desktop transfer and additional-storage budgets are fixed at 512 MiB each. Files reported as possible misses by the last explicit compile are included in the next check for that exact project snapshot; this does not prove they are required. Dependencies that cannot be resolved statically remain visible as an uncertainty note.

Preparation starts only when the user chooses its action; it prepares automatically detected and manifest-declared known resources and never compiles. **Cancel** stops and reaps that preparation. Closing the dialog hides its view and visible progress while the job can continue; it does not cancel the job. Progress listeners remain active at the app-hook level while mounted and are removed when the hook unmounts.

## Desktop workspace adapter

The desktop backend exposes `resources_workspace_operation` with a single `request` object. Its schema is camelCase and rejects unknown fields: `operation`, `jobId`, `engine`, nullable `projectRoot`, `mainFile`, `overlays`, `allowedRoots`, `workspaceIdentity`, and optional typed `selection`, `expectedInputDigest`, `expectedPlanDigest`, `cursor`, `limit`, `maxDownloadBytes`, `maxStorageBytes`, and `templateAssets`. Supported operation names are `resources.analyze`, `resources.plan`, `resources.list`, `resources.prepare_project`, `resources.cache_list`, and `resources.cache_remove`. Cache operations add optional `expectedCacheDigest` and `removePaths` fields. Dirty text overlays, including `sciencebatch.resources.json`, are applied before analysis and preparation. The opaque workspace identity participates in the resource input digest.

Read-only analysis runs from the captured snapshot on a blocking worker thread. Preparation registers its job before snapshot capture and passes the same explicit-download permission, expected digests, selection, and budgets to the shared automation service. `project-resources-progress` events use the caller's `jobId`. Closing the dialog hides its UI and visible progress without cancelling an active preparation; the app-lifetime hook keeps receiving progress while mounted and removes its event listener when unmounted. `cancel_project_resources({ jobId })` requests cancellation and waits for the operation and isolated worker cleanup. On application exit, new workspace jobs are rejected, active resource and compile jobs are cancelled, and the app waits for their isolated workers to be reaped before exiting.

`templateAssets` accepts `starter-latex` or `starter-typst` only for a rootless virtual snapshot and only when its engine matches. The grant adds the fixed sample bibliography and image files to that captured snapshot. Disk-backed projects cannot receive a template grant, and user-provided overlay files at those paths take precedence. Project-folder creation is new-only: it rejects existing targets and creates every initial file with create-new semantics, propagating errors instead of overwriting prior project contents.

Workspace operation errors serialize as `{ "error": PublicError, "diagnostics": [...] }`, retaining the shared automation service's error code, message, details, exit code semantics, and diagnostics. Successful resource calls return the shared operation data value without a transport-specific wrapper. `compile_workspace_snapshot` and the legacy explicit compile invoke both use captured in-memory snapshots and the shared isolated offline compiler path; source changes and resource operations never trigger compilation.

## Installed resources

**Manage installed resources** in Dependencies opens a separate shared-cache inventory. Its list is paged in batches of at most 200 entries and can filter loaded paths. The window reports cached resource bodies, bundle metadata, built-in resource payload, and other compiler cache storage separately. Built-in resources, metadata, formats, and caches outside the pinned catalog are read-only in this manager. Listed cache files are not advertised as hash-verified solely because they appear in an inventory.

Only explicit selection and confirmation remove cache files. The current captured project's detected and declared resource files are protected. This protection does not establish that other projects do not use a file: the cache is shared, and those projects may need an explicit download later. No persistent cross-project usage history or automatic cleanup is added.

`resources.cache_list` returns `cacheDigest`, `bundleDigest`, `offset`, `total`, `nextCursor`, `items`, and `summary`. Each item includes `path`, `bytes`, `requiredByProject`, and `removable`. The summary includes `installedFiles`, `installedBytes`, `metadataBytes`, `otherBytes`, `embeddedFiles`, and `embeddedBytes`. Sizes are logical byte lengths, not filesystem allocation measurements. Cursors bind the inventory digest. Inventory reads never compile, download, create directories, or change permissions.

`resources.cache_remove` requires edit permission, an exact `expectedInputDigest`, `expectedCacheDigest`, and one to 200 distinct `removePaths`. It resolves the captured snapshot again, checks the installed inventory, and validates the complete selection before deleting. Only pinned cache body paths are eligible; traversal, symbolic links, foreign ownership, stale inventories, and protected files are rejected. The response reports `removedFiles` and `removedBytes`. A filesystem failure during the deletion loop reports any partial removal; the operation does not promise filesystem transactions.

Removal shares cache writer coordination with preparation. Explicit LaTeX compiler workers hold a shared cache reader lease until their subprocess is collected, including cancellation or a dropped caller. An occupied lease causes bounded waiting or a retryable error. Closing an inventory window never starts cleanup, and analysis, preparation, and deletion never compile.

On non-Unix platforms, inventory is read-only and every row is non-removable until deletion has equivalent handle-based path validation. Cache management can be opened from either LaTeX or Typst projects; current snapshot and inventory guards apply in both cases.
